# B2 — Explorable biological structures (proposal)

Status: accepted direction (2026-11-11). Each step below still gets its own short design note before code.

## 1. Purpose

SVF exists to give students 3D learning structures, mostly for biology. It
covers the structural side that a maths and simulation engine does not. The
test is generality: **a heart today, a cockroach tomorrow, a plant stem the day
after**, without a new project each time.

The learner questions that define success:

| Lesson | The learner should be able to |
|---|---|
| Heart (A level) | name each part, turn the heart in 3D, look past the outer wall into the chambers and valves |
| Plant stem or leaf (O/A level) | see the tissue layers and how they are arranged, in a transverse and a longitudinal section |
| Cockroach dissection (O level) | identify external features, then remove layers in dissection order and identify the internal organs |
| Chemistry bonding (A level) | already covered in principle by the VSEPR case, which builds shapes from rules rather than data |

## 2. Why not just adopt glTF

If lessons only used existing models, a glTF viewer would be enough and SVF
would not be justified. A glTF file carries shapes and part names. A lesson
also needs:

- **meaning**: what a part is, what it does, what it contains or connects to;
- **layers**: the order of going beyond the surface (exoskeleton, fat body,
  gut; or epidermis, cortex, vascular bundle, pith);
- **lesson operations**: section here, remove this layer, isolate that part,
  label these;
- **authoring**: a teacher or author must be able to *make* a structure that
  has no dataset, and make it light.

glTF and VTK stay as inputs that can be adapted. They are not the product.

## 3. The structure model

One SVF structure is a small text document:

- **Parts**: a tree (organism → system → organ → tissue), each with an id, a
  name, a short description and a display colour.
- **Relations**: typed links between parts (contains, connects to, opens into).
- **Layers**: ordered groups of parts for peeling or dissection.
- **Views**: named lesson views (camera, visible parts, section plane, labels).
- **Geometry per part**, from exactly one source:
  - **Recipe**: generated by SVF from building blocks (section 4). Light,
    exact and editable.
  - **Adapted**: derived from a dataset (for example the Rodero heart's 24
    tags), simplified and saved as a light surface.
  - **Imported**: a part taken as-is from glTF/OBJ, keeping its provenance.
- **Provenance**: for recipes, the reference the structure follows (textbook,
  syllabus, paper); for data, the source and licence, as B1 already requires.

Geometry generation stays in `svf-core` (f64, graphics-free, testable).

## 4. Authoring building blocks

A deliberately small set, chosen from the four lessons:

| Block | Used for |
|---|---|
| Tube along a curve with a radius profile | vessels, gut, trachea, nerve cord, leg segments, veins |
| Shell / ellipsoid / lofted profile | chambers, body segments, head capsule, cells |
| Layered extrusion of a 2D profile | stem, root, leaf blade, tissue layers |
| Repetition and mirror symmetry | abdominal segments, paired legs, vascular bundles, stomata |

Each block produces closed, named surfaces with known inside and outside, so
that sections and picking work the same for every organism.

## 5. Lesson operations

- show, hide and isolate a part or layer;
- pick a part to show its name and description;
- **section plane** with **capped** cut faces, so tissues read as filled
  regions, not hollow outlines;
- layer peeling in the authored order (dissection);
- simple labels attached to parts.

Capping is the main technical risk. For recipe parts the cap is known exactly
(for an extrusion, a transverse cut is the profile itself). For adapted and
imported parts it needs closed-loop extraction and triangulation of the cut.

## 6. Shape shading (a camera headlight)

The renderer is unlit, so 3D anatomy reads as flat silhouettes (see the B1.2
evidence images). Shape cannot be judged without shading. This is **not** a
lighting system: no light objects, materials, shadows or editors. It is one
light fixed to the camera, computed in `mesh.wgsl` from each triangle's own
facing (screen-space derivatives of the world position), so no vertex normals
and no new mesh data are needed. Estimated change: the mesh shader plus one
camera field in the uniform. Lines stay unlit.

Caveat: shading changes brightness, which distorts colour-mapped data (for
example RHO on Viridis). Shading must therefore be switchable per surface and
stay off by default where colour encodes a value.

## 8. Acceptance for the first proof (dicot stem)

- The structure file is authored by hand, is under a few kilobytes and cites
  its reference.
- A learner view shows epidermis, cortex, a ring of vascular bundles (xylem and
  phloem distinguishable) and pith; each is pickable by name.
- A transverse and a longitudinal section show the layers as filled regions.
- Judged by the learner question: could an O-level student name the tissues
  and say how bundles are arranged in a dicot stem, from the view alone?

## 9. Non-goals

Photorealism, textures, lighting rigs, shadows, a graphical editor (authoring
is a text file first), animation, simulation, and integration with other
products.

## 10. Decisions

1. Geometry comes from three sources: recipe, adapted, imported.
2. Structure files are RON: it maps directly onto Rust types and allows comments.
3. The headlight is in scope as defined in section 6 and goes no further.
4. Order: headlight, stem, sections and peeling, cockroach, heart.
5. No curriculum anchoring at framework level; that belongs to the lessons
   built on top.
